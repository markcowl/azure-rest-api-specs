# LRO Response Mismatch Rule Evaluation

Evaluation of violations reported by the new linter rule
`@azure-tools/typespec-azure-resource-manager/lro-response-mismatch`
(introduced in [Azure/typespec-azure#4145](https://github.com/Azure/typespec-azure/pull/4145))
when run against the `typespec-next` branch of `Azure/azure-rest-api-specs`.

## What the rule checks

For every ARM long-running operation (LRO) the rule compares the **encoded `finalResult`**
(the type the LRO actually resolves to on completion, derived from `getLroMetadata`) against the
**expected** result for that operation shape:

- **PUT / PATCH** lifecycle operations must resolve their `finalResult` to the **resource type**.
- **POST** actions must resolve their `finalResult` to the action's **intended response** (the body
  of any 200 response the action declares).
- **DELETE** operations must resolve to **void** (nothing is returned on the wire).

A mismatch means the on-the-wire final result differs from what the operation's author intended.

## Method

1. Installed the PR's candidate packages (pkg.pr.new build of #4145) plus the matching
   `typespec-next` dev-version pins into `azure-rest-api-specs`.
2. Compiled each affected spec with `npx tsv <dir>` / `tsp compile --warn-as-error`.
3. Captured, for every violation, the rule's computed `finalResult` and `expected` type
   (ground-truth instrumentation of the rule), then classified each against author intent.

## Determinations

Every violation is classified as one of:

- **user-error** — the encoded `finalResult` is genuinely not what the author intended
  (the rule correctly caught a modeling bug). These are suppressed in-place with
  `#suppress "@azure-tools/typespec-azure-resource-manager/lro-response-mismatch" "fixme-invalid-lro-result"`.
- **false-positive** — the encoded `finalResult` matches the author's intent; the rule is wrong.
  These are **not** suppressed and remain visible.
- **indeterminate** — intent could not be established. (None in this evaluation.)

non-void final result (e.g. `OperationStatusResult`) that is not actually returned on the wire.

## False positives (rule incorrectly flagged; not suppressed)

These operations return exactly what their author intended; the rule's expectation is wrong.

- **Body-returning DELETEs** — legacy operations that deliberately return the deleted resource /
  connection body on the wire for backward compatibility. The declared response body matches the
  encoded `finalResult`, but the rule flags any non-void delete final result.
- **Legacy parent-modeled sub-resource PUT** — `PrivateEndpointConnection.createOrUpdate` in
  API Management correctly returns the sub-resource it creates, but the rule compares against the
  interface's parent resource type.
