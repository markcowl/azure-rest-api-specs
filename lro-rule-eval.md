# LRO Response Mismatch Rule Evaluation

Evaluation of violations reported by the new linter rule
`@azure-tools/typespec-azure-resource-manager/lro-response-mismatch`
(introduced in [Azure/typespec-azure#4145](https://github.com/Azure/typespec-azure/pull/4145))
when run against the `typespec-next` branch of `Azure/azure-rest-api-specs`.

## What the rule checks

For every ARM long-running operation (LRO) the rule compares the **encoded `finalResult`**
(the type the LRO actually resolves to on completion, derived from `getLroMetadata`) against the
**expected** result for that operation shape:

- **PUT / PATCH** lifecycle operations must resolve their `finalResult` to the **resource type**.
- **POST** actions must resolve their `finalResult` to the action's **intended response** — the
  type named by the operation template's `Response` parameter, or the body of the action's 200
  response (a 204 / no-body action resolves to void).
- **DELETE** operations must resolve to **void** (nothing is returned on the wire).

A mismatch means the on-the-wire final result differs from the convention for that operation shape.

## Method

1. Installed the PR's candidate packages (pkg.pr.new build of #4145) plus the matching
   `typespec-next` dev-version pins into `azure-rest-api-specs`.
2. Compiled each affected spec with `npx tsv <dir>` / `tsp compile --warn-as-error`.
3. For every violation, captured the rule's exact computed `finalResult` and `expected` type by
   reading `lroMetadata.finalResult` via `getLroMetadata` (ground-truth instrumentation of the
   rule), then classified each against the author's intent. No values were guessed.

## Determinations

Every violation is classified as one of:

- **user-error** — the encoded `finalResult` is not the value the operation's shape requires, and
  the encoding reflects either a genuine modeling mistake (e.g. a PATCH resolving to `void`, a POST
  action double-wrapping its response) **or** a deliberate but non-idiomatic deviation (e.g. a
  body-returning DELETE, a PUT resolving to a sub-resource). In both cases the rule correctly
  flagged a real deviation, so it is suppressed in-place with
  `#suppress "@azure-tools/typespec-azure-resource-manager/lro-response-mismatch" "fixme-invalid-lro-result"`.
- **false-positive** — the rule fired even though the encoded `finalResult` **actually matches** the
  required value (a DELETE whose `finalResult` really is `void`; a PUT/PATCH whose `finalResult`
  really is the resource type). This would indicate a computation bug in the rule. **None were
  found:** every flagged operation was confirmed via `getLroMetadata` to encode a value that
  genuinely differs from the convention.
- **indeterminate** — intent could not be established. (None in this evaluation.)

## User errors (rule correctly flagged; suppressed with `fixme-invalid-lro-result`)

These are all real deviations from the convention for their operation shape. They fall into two
groups, both requiring suppression:

- **Genuine modeling mistakes** — PUT/PATCH LROs that resolve to `void` instead of the resource,
  and POST actions that double-wrap or drop their intended response type.
- **Intentional non-idiomatic deviations** — DELETE LROs that encode a non-void body (e.g.
  `OperationStatusResult`, a named result model, or `unknown`) that is returned on the wire, and a
  PUT that resolves to a sub-resource rather than the resource. These reflect the API's real
  behavior but are still flagged because they break the ARM LRO convention; the suppression records
  that the deviation is deliberate.

### Correcting violations instead of suppressing

Suppression records that a deviation is known; it does not fix the underlying model. Each violation
below carries a per-row **How to fix instead of suppress** column. The fixes fall into these
families:

- **DELETE returns a body** (should be `void`): switch to a void-returning delete template
  (`ArmResourceDeleteWithoutOkAsync` / `ArmResourceDeleteSync`) and drop the response body, or set
  `FinalResult = void`. Genuinely body-returning deletes are non-idiomatic; removing the body is a
  breaking change, so these stay suppressed until it can be dropped.
- **PUT/PATCH resolves to `void`** (should be the resource): use the standard async lifecycle
  template (`ArmResourceCreateOrReplaceAsync`, `ArmResourcePatchAsync` / `ArmCustomPatchAsync`) with
  default headers, or set `FinalResult = <Resource>` on the async header.
- **PUT resolves to a sub-resource**: model the create on the sub-resource itself so the resource
  type and `finalResult` agree, or set the `201` `FinalResult` to the attached resource type.
- **POST action passes an `ArmResponse<T>` envelope as `Response`**: `ArmResourceActionAsync` already
  wraps `Response` in the `200` envelope, so pass the bare payload — `Response = T` instead of
  `Response = ArmResponse<T>`. The envelope carries HTTP metadata; the intended `finalResult` is the
  bare `T`. (Where the wrapped type is `ErrorResponse`, also replace it with the real success type.)
- **POST action resolves to `void` via custom `LroHeaders`/`final-state-via`**: either move to the
  standard `ArmResourceActionAsync<Resource, Request, Response>` (default headers wire `finalResult`
  to `Response`), or set `FinalResult = <Response>` on the header that is the intended terminal state
  (e.g. `ArmAsyncOperationHeader<FinalResult = <Response>>` when `final-state-via` is
  `azure-async-operation`). If the action truly returns nothing async, change `Response` to `void`.
- **POST action declares both a `200`-with-body and a `204`**: keep one terminal shape — the `200`
  with the body, or the `204` with no body — not both.

## False positives (rule incorrectly flagged)

**None.** A false positive here would require the rule to flag an operation whose `finalResult`
already matches its convention — a DELETE that genuinely resolves to `void`, or a PUT/PATCH that
genuinely resolves to the resource type. Every flagged operation was checked with `getLroMetadata`
and confirmed to encode a value that really does differ from the convention, so the rule's
computation was correct in all 96 cases. No rule fix is warranted by this data set.

Note the POST envelope cases specifically (`Response = ArmResponse<T>`): although the envelope's HTTP
body is `T`, `ArmResponse<T>` is a response envelope carrying status/headers, while the intended
`finalResult` is the bare payload `T`. Encoding the envelope is a genuine authoring error, so the
rule is acting as intended — these are user-errors, not false positives.
