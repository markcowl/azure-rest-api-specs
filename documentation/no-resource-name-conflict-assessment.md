### Root causes

1. **The same model at more than one scope or parent without distinct names** (Authorization by-ID, Compute, DevCenter, KeyVault, Marketplace, PolicyInsights, Security, Support). A Legacy `LegacyOperations`/`ExtensionOperations` interface is legitimately needed for the second path, but it derives the same logical name as the first.
2. **Child or sub-path operations written with the parent's templates plus extra path parameters** (APIM, Automation, CognitiveServices, ComputeBulkActions, Cosmos DB, HDInsight, IoT Hub, SiteRecovery). The operation's path and ARM type are a child (`.../jobs/{jobId}`, `.../azureasyncoperations/{id}`), but its resource identity — and therefore its name — is the parent's.
3. **An explicitly duplicated `ResourceName`** (ContainerApps, PolicyInsights, SiteRecovery).

### Fix mechanisms

| Mechanism                                                                                                                                      | When to use                                                                                            | Findings                                |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| `ResourceName = "..."` on a `Legacy.LegacyOperations`/`ExtensionOperations` alias or interface                                                 | The second path really differs from the model's `@autoRoute` path, so the Legacy interface is required | #7–#9, #18, #19, #23, #24, #32, #37–#49 |
| `OverrideResourceName = "..."` on a Legacy _operation_ template (`CreateOrUpdateSync`, `CreateOrReplaceAsync`, ...)                            | A single Legacy operation that targets a sub-path of its resource                                      | #1–#6, #17                              |
| Name argument on the standard decorator at the use site: `@armResourceRead(Model, "Name")`, `@armResourceCreateOrUpdate`, `@armResourceDelete` | Standard `ArmResource*` templates (or custom ops) that target a sub-path                               | #10–#16, #20–#22, #25–#31, #33–#36      |

Simpler alternatives were considered for each finding, in line with the preference to avoid Legacy interface templates. For root cause 1, the Legacy interface is the mechanism for the additional path, so it stays and only gains a name. For root cause 2, the more correct model — a separate `ProxyResource` child with standard templates — needs a resource-envelope model at that path. The current responses (`JobStream`, `AsyncOperationResult`, linked contracts, ...) aren't envelopes, so that would change Swagger. The name argument is the minimal, contract-preserving fix; each finding's **Assessment** says where a larger refactor would be more correct.

**SDK naming caveat:** the logical resource name feeds management SDK resource naming. Pick names that match the existing SDK class names, or add `@@clientName` in `client.tsp`, before applying. PolicyInsights (#37–#41) deliberately shares one name across scopes (`@@clientName(..., "csharp")` in `client.tsp`), so review it with SDK owners first.

## Method and interpretation

- **Released tooling:** ARM library `@azure-tools/typespec-azure-resource-manager@0.74.0` and the snapshot's frozen `pnpm-lock.yaml`. See the [rule documentation](https://azure.github.io/typespec-azure/docs/libraries/azure-resource-manager/rules/no-resource-name-conflict).
- **Rule behavior:** the rule groups `resolveArmResources(program).resources` by logical `resourceName`, considers only resources with an authored read or createOrUpdate, and reports the second and later resources with the same name. It is off by default in this release, and its diagnostics can't be suppressed, so each needs a source fix.
- **Discovery and entrypoints:** every directory with a tracked `tspconfig.yaml` is a spec. The entrypoint is the `tspconfig.yaml` entrypoint if any, otherwise `main.tsp`, otherwise a legacy `client.tsp`. Where `main.tsp` was used and a `client.tsp` exists that `main.tsp` doesn't import, `client.tsp` was compiled separately.
- **Evaluation:** each entrypoint was compiled with no emitters and only this rule enabled. Compiler and library errors were retained.
- **Counting:** 671 entrypoints were compiled: 621 clean, 24 with violations, 26 blocked (see coverage). Duplicate reports from overlapping entrypoints (for example, a parent `client.tsp` and a child `main.tsp` compiling the same sources) were deduplicated by diagnostic source location and resource name, giving {{COUNT}} findings. Each finding lists every ARM resource sharing the name, with the authored read, createOrUpdate and delete operations of each. One fix can resolve several findings, and some findings need edits to more than the diagnostic's operation.
- **Fix verification:** each fix was applied to the snapshot. The rule was re-run (0 conflicts for the project), the project was recompiled and re-emitted with its configured OpenAPI emitter, and `git status` confirmed that only `.tsp` files changed (no Swagger diff). New warnings were checked against the baseline. Prototypes were reverted. Snippets show only the changed lines; `/* existing ... */` marks arguments to keep.

**Suggested fix:** Give the link operation its own logical resource name with `OverrideResourceName` on the Legacy operation template (`GroupContract.tsp:334`).

```tsp

  GroupContract,
```
